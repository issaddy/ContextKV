# ContextKV：课题闭环审查与阶段实施指导

审查日期：2026-11-04。对象：`codex/context-budget-loop@d6f142436e1a258b633543b4793b07873fa40bcd`，共 250 个受版本控制文件。该分支已经包含 PR #1 的修正，并比 `main@702ebe9` 多 86 个提交。本文区分最新实现、已有测量、本轮纠正和下一阶段工作；数值依据为 [预算阅读记录](budget_loop_20261103.json)。

## 1. 总体判断与研究目标

课题具有成立的应用场景和系统逻辑，A 已有明显阶段收益；A/B/C 的统一联合收益尚未完成验证。接下来收敛到三个主模块：任务与证据上下文、预算化阅读决策、原生 KV 保留。辅助训练和评价分别服务这三个模块。

四个目标：

1. 在固定 Qwen3-32B 下，把多轮条件、来源、事实和最终回答正确连接。
2. 让原文阅读产生可跨轮复用的真实因果前缀。
3. 用可实现的最终回答收益决定下一步计算和保留期限。
4. 在同一版本、同一队列和同一资源配额下，给出质量—响应时间—总在线资源的可比结果。

### 研究对象为何需要跨层协同

| 对象 | 负责的决定 | 本课题的位置 |
|---|---|---|
| Agent | 任务分解、工具调用、业务流程 | 调用本系统，也可以由普通问答前端调用 |
| RAG | 从外部资料检索并支持回答 | 本系统采用的应用形态与资料入口 |
| 上下文管理 | 使用哪些历史、条件、资料和事实；怎样组成每次模型输入；何时继续阅读 | A 与 B 的核心 |
| 推理引擎 | 执行给定 token 请求、调度计算、管理实际 KV 页 | 复用 SGLang；C 提供来源价值与保留决定 |

RAG、agent 与本课题可以组合。上下文管理属于应用和推理编排层，KV 属于执行层，二者通过**实际 token 序列、因果前缀、已观察成本与后续资料需求**相连。相同文字放到不同前文之后，通常不能直接复用原来的精确 KV；删除、重排或重写上下文会改变复用机会。只按语义选最短输入可能增加预填充，只按命中率保留最长历史又可能引入无关资料。协同优化的对象正是这组取舍。[SGLang 原文](https://arxiv.org/abs/2312.07104)已将 KV 复用用于 RAG、复杂程序和多轮对话；[CacheBlend](https://arxiv.org/abs/2405.16444)则是非前缀复用的另一类实现，本项目当前采用精确原生前缀路径。

KV 的作用是减少计算与回载；在输入和生成规则不变时，它本身不增加答案知识。质量收益来自更好的证据和阅读，或者在同一时间/资源配额内完成更多有价值的阅读。缓存节省不能增加模型上下文上限，也不能把已执行 token 从累计 token 账本中扣掉。

### 云端场景与研究边界

适用场景是同一文档集合上的连续追问、跨文档比较、条件修正、版本切换、长资料汇总，且 GPU/Host KV、并发或完整响应时间受限。研究单元可以是云端一个受限 SGLang 副本或服务池，agent 在任意机器通过 API 调用会话协调器。

当前已有 `/sessions/{session_id}/query` 和 `/turns` 入口；完整 C 还需服务端 `/cache/quote`、`/context/prefix/*`。服务部署在云端并不妨碍协同；能否控制上下文与缓存接口才决定能实现哪一部分。普通封闭模型 API 可以实施 A/B 中可观察的部分，完整 C 由可管理推理服务的一方实施。集群路由优先复用 [SGLang Model Gateway](https://github.com/sgl-project/sglang/tree/main/sgl-model-gateway)，不新增论文模块。

当前补丁的 `get_runtime` 对应单 worker、TP/DP/PP=1 的 dense FULL Python TreeCore；物理资源采样使用服务节点的 `nvidia-smi`、`/proc`。本轮证据对应这一执行范围。任意独立短问题、来源几乎不重访的负载应作为低复用对照；云集群 TP/PD 的扩展属于之后的工程适配。

## 2. 最终模块与训练边界

| 模块 | 输入与输出 | 主要机制 | 主要验收量 |
|---|---|---|---|
| A：任务与证据上下文 | 当前问题、实际历史、原文目录 → TaskState、EvidenceSet、规范来源片段与事实 | Need 的条件/主体/版本绑定；证据依赖闭包；共享提取；事实及来源链；操作无关来源前缀 | 完整队列质量，条件与事实正确率，有效正文覆盖，总 READ token |
| B：预算化阅读决策 | 证据、已得事实、缺口、已付费用、原生报价 → 下一步 READ/GAP/REDUCE/ANSWER | 最终窗口份额；CPU 确定性聚合；有限模型归约；有界后续收益；滚动执行 | 决策遗憾，提前停止错误，最终质量与完整在线成本 |
| C：原生 KV 保留 | 稳定来源路径、原生驻留/压力、预计重访 → keep/release/renew、新保留期限 | 原生 Radix/HiCache；新旧 owner 共同容量竞争；共享页并集；同一读取事件收益去重 | 实际正文命中/回载/重算，控制与驻留净收益，联合 P95/goodput |

原文档案、结构化语义状态和物理 KV 是三个对象。`SourceSpan/SourceDirectory` 保存原文及坐标，`TaskState/ReadingOutcome/Claim DAG` 保存任务与已得事实，SGLang 保存对应实际前缀的 KV。它们通过来源身份和真实输入关联。

Qwen3-32B 权重与解码继续冻结。当前代码已经移除 Qwen 训练入口，`reader_audit` 用于核验协议。允许训练的辅助对象包括：

- BGE-M3 查询侧适配与任务头；文档编码器和索引按声明范围复用。
- BGE reranker 的支持关系及集合效用；P1 集合偏好阶段冻结已训练的支持编码器/头。
- B 的最终收益和分支成本回归。
- C 基于原生配对轨迹的价值估计。

这些训练按瓶颈需要开展。固定 Qwen 也在承担部分在线任务解释，其计算属于在线资源；小模型替代这一调用的价值是保留任务语义质量并降低完整成本。

## 3. 本轮发现与纠正

### A1：每个 Need 的条件关联被解释器覆盖——已纠正

`adapters/history_state.py::TaskInterpreter.interpret` 原来把全部活动条件写入每个 Need，覆盖 teacher 已给出的独立关联。

CPU 复现：“Count employees in 2023 and sum revenue in 2024.” 原 prediction 为 count→2023、sum→2024；解释后两者同时绑定 2023 和 2024，两个支持查询都含两个年份，`numeric_read_scopes` 将它们合为同一 scope。

本轮保留显式 Need—condition 边，REPLACE/REMOVE 仅改写引用相应条件的 Need；ADD 由当前 Need 显式关联，共享条件由多个 Need 引用同一 ID 表达。无条件 Need 保持为空。已有 schema 足够，增加了 7 项集中语义验证。

保存的标签同时含 `prediction` 与 `task_state`。优先利用原 prediction 和实际历史，按会话重建受影响的 TaskState；仅重采输入实际改变的支持监督和奖励。原始预测中已有正确关联时无需重新调用 teacher。

### A2：source_first 还不是稳定跨轮前缀——下一阶段首要协同改进

`reading.build_read_plan` 根据当前任务/历史剩余容量重新切原文；`stable_source_payload` 把含结束坐标的 hash 放在正文之前。相同资料只因问题变长，就会在正文开始前产生不同 token。

本轮 ByteTemplate 结构探针，固定 9000 READ 输入份额，问题从 15 字符变为 996 字符：

| 表达方式 | 两轮 READ 次数 | 首片原文范围 | 两轮首片公共前缀 | 公共原文正文 |
|---|---|---|---:|---:|
| 当前动态切片 | 7 / 10 | 0:3974 / 0:2993 | 264 | 0 |
| 只将动态标识放到正文后 | 7 / 10 | 同上 | 3319 | 2993 |
| 固定 2500 字符窗口 | 11 / 11 | 均为 0:2500 | 3360，完整相同 | 2500 |

这是输入结构验证，数值不是 Qwen tokenizer 或 GPU 性能测量。它证明动态标识提前会破坏首片复用，固定窗口可稳定身份，同时也显示小窗口可能增加调用次数。

另一个同源问题：`stable_prefix_messages` 的数值分支把数值提取协议和 shared 示例放在系统前缀中，并使用与 generic 分支不同的来源 schema。因此 count/sum、普通提取、多跳之间也没有统一的来源前缀；旧跨操作前缀测试仍在失败。

实施应复用既有 SourceSpan、source_aliases 和 ContextPlan：按文档版本、实际 tokenizer、段落/表格边界建立规范来源窗口；来源段只包含操作无关信息；问题、历史、数值/bridge 指令及输出协议放到来源之后。B 在既有任务和输出预算内选择完整来源窗口，C 对这些实际路径估值。先选一档窗口粒度，按总 READ 调用、总 token、质量和实测预填充比较，不引入新的分块层级框架。

### A3：辅助训练尚未提供可采用的增益

记录显示任务头 Need 字符 F1 为 0.24938；operation 指标为整个 Need 操作列表精确匹配，值为 0，当前未部署。查询 LoRA 的 Recall@20/50 与 P0 相同，分别为 0.86111/0.91667。P1 set-only 的 Q40=0.5325，低于 P0 shared=0.61；冻结 P0 是当前正确选择。

`training/task_model.py` 仍缺 Need—condition、Need—subject 关联监督及完整 scope/predecessor 输出，不能仅根据 TaskState 类型推断学生模型已学会这些语义。先固定输出契约，再决定替代教师的训练方式。

利用已保存候选答案，先计算候选最优值 `max Q(candidate)`，分别与 P0、P1 相比。候选最优值低，改检索/证据候选；候选有高质量答案但 P1 选错，改支持或排序；事实在 READ 中丢失，改阅读；正确归约在 ANSWER 中失真，改最终结论使用。按这一分解决定训练对象，不直接扩大训练轮数。

### B：单动作立即回答无法学习多跳的延迟收益

`action_policy.py`、`train_plan_gain.py` 的 `observed_actions` 现在严格比较一次 READ/REDUCE/GAP 后立即 ANSWER。它能学习局部停止；若第一个 READ 仅找到桥接实体，还需 GAP→READ 才获得终端答案，一步分支可能只有正成本、质量差约为零，策略会偏向提前停止。

全资料覆盖任务的扫描由 `mandatory_coverage` 固定完成。因此当前 B 的作用范围主要在可选择的证据阅读/归约/回答阶段，尚未优化完整长文扫描本身。

已完成 B 采集包含 210/48 个 train/dev 决策状态、306/65 个有效收益对，开发 ΔQ MAE=0.07591。这是预测指标。采集当时排除了 178 个初始观察，最新代码已允许初始状态，但尚未重采。

下一步复用现有 Need 前驱和有限 DAG，给首个动作一个**固定、有界的后续执行策略**，或者少量有语义完成点的复合候选，如 READ→缺口→READ。监督最终回答质量差及完整分支成本；线上仍执行一步后重新观察。先验证桥接事实、已足够回答、无效补检索三类状态，再采集初始状态和实际中间状态。评价动作选择遗憾、停止错误和净成本，避免只看回归 MAE。

### C1：低收益旧保护挡住高收益新前缀——已纠正

原 `_allocate_value` 先选择正收益旧 lease，再将它们锁为 protected 分配新候选。GPU 只容纳一页，旧 A 收益 10、新 B 收益 100 时，仍保留 A。

本轮把旧 lease 的 keep、renew 和新前缀放入同一次容量分配。keep 使用剩余期限、无需续租调用；未选旧项释放，选中新项或续租才发控制请求；同 owner 仍只选一个期限，共享页和读取事件继续去重。5 项语义验证覆盖替换、保留、续租和重叠页面/收益。

### C2：价值资产还没有开发覆盖

已完成四个窗口、十六个原生/TTL arm；训练两窗口中仅一个有合格来源正文干预，其 TTL15/60/180 产生三个 profile。独立有效训练窗口是一个，不是三个；开发六个比较均可测量，但 calibrated=0/6。

先完成稳定来源输入，再从目标负载抽取独立窗口，覆盖真实重访间隔、GPU/Host/重算及不同压力。多个 TTL 是同一窗口的干预，统计划分按独立窗口/会话进行。观察到的未来只进入离线标签，在线使用当前状态和过去记录。原生软优先级 release 不等于立即释放物理 KV，资源收益以实际回执和采样积分计量。

当前经验模型按 11 个特征精确分桶，单窗口数据无法形成开发覆盖。`source_demand_event_key` 以第一个正文因果页近似读取事件，也可能把共享首个来源、后续路径不同的两个重访合成一个。下一阶段以规范 READ 窗口定义需求对象与重叠关系，校准少量可泛化的状态特征；同时测量被挤出来源的代价。当前 GPU/Host 价格为零，目标读取节省不能替代完整窗口的资源净收益。

## 4. 已有结果应怎样解释

350 题、77 会话的已登记结果：

| 指标 | 登记基线 | 冻结前 P0 shared 候选 |
|---|---:|---:|
| 全声明队列 Q | 0.445090 | 0.657540 |
| 交付 | 300/350 | 341/350 |
| 原生 reader token | 11,941,836 | 7,520,143 |
| 原生 reader 调用数 | 2,487 | 2,585 |

质量提高 21.245 个百分点，reader token 减少 37.03%。其中构造长文从 0 到 0.55，贡献总 Q 的 13.75 个百分点，说明阅读可交付性与协议改进已经有效。当前协议的 isolated 对照 Q=0.496961、交付 301/350、reader token=13,605,223，也应随结果呈现。

这一综合 Q 的 55% 权重来自公开 MultiDoc2Dial/MT-RAG 开发轨，45% 来自项目构造的版本/长文机制轨。它是项目开发综合分。dev 中的 `loong` 键实际为构造长文，test 才是公开 Loong。保持登记权重，公开 benchmark 逐项报告原指标，构造任务单列机制效果。

候选汇总使用多个组件源码快照，MultiDoc2Dial 登记为 `607e02d`，长文使用之后的 per-Need 选择；原基线还有在线解释与离线评分重叠负载。完整冻结版本下的 B×C 四格、可比 P95 和全部在线物理资源结论尚待完成。37.03% 不能直接改写为显存或全部推理费用降幅。

长文当前精确正确 11/20、交付 15/20；五个未交付为 1 个 READ 截断、3 个单位不兼容、1 个量值冲突，另外四个交付答案错误。按实体群体、量值/单位、Need 选择、CPU 归约、ANSWER 使用定位这九题，单位语义与来源群体正确后再聚合。保留有意义的确定性计算，不用忽略不兼容量值来提高完成数。

## 5. Benchmark 的上下文从哪里来

1. `adapters/doc2dial.py::benchmark_rows` 等适配器建立 conversation/task/turn。检索型任务把资料放进独立语料索引，原始 `contexts=[]`；给定多文档任务则在 `contexts` 携带原文。
2. `bench.study.run_dataset` 按会话排序问题；每轮从 SessionStore 读取本方法已提交的 `raw_history`。
3. `StudyEvidenceProvider.retrieve/retrieve_supplied` 使用当前问题和实际历史，形成 Need、条件、资料集合及阅读计划。这里已经发生上下文管理。
4. `Controller.serve_turn` 与 `execution.py` 执行 READ/REDUCE，记录结构化事实及来源，再编译 ANSWER。B 可在中间状态选择后续计算。
5. `engine_client.generate` 把该次具体 `input_ids`、输出份额和采样参数发送至 SGLang。引擎负责执行；C 查询并控制对应实际前缀。
6. `SessionStore.commit_turn_and_outbox` 提交一次实际 QA。下一轮读取这个实际回答及任务状态；来源目录和 KV 各自保留自己的数据。

例：会话给出政策文档 A、补充条件 B、费用表 C。第一轮问申请条件，第二轮问“如果改为某地区呢”，第三轮问“这些费用合计多少”。任务条件随问题更新，A 选择相应原文，B 读取/聚合，答案写回历史；再次需要 A/B/C 中同一稳定来源窗口时，C 尝试复用它的已执行因果前缀。benchmark 的职责是提供这组资料和问题、逐轮驱动系统并计分，不要求 SGLang 自己理解数据集。

官方固定作者历史与项目 P3 实际历史是两条评价轨。P3 让每种方法使用自己的实际答案；官方历史轨使用作者给定前缀。公开 MT-RAG、MultiDoc2Dial 有多轮文档任务，[MT-RAG](https://arxiv.org/abs/2501.03468)、[MultiDoc2Dial](https://aclanthology.org/2021.emnlp-main.498/)。Loong/2Wiki 等补充长文或多跳能力，独立题逐条执行不自动形成多轮记忆实验。

当前 `capacity_workflow --full-queue` 未接入 workload-plan，计时在取得并发槽后开始，属于固定并发闭环服务时间。最终排队/P95实验复用现有 WorkloadDispatcher，固定请求到达与停顿，计入槽前等待，报告完成率、完整响应 P95、SLO goodput 和会话累计时间。在线 reader、任务解释、检索/支持、控制费用以及整批 GPU/Host GiB·s 共同报告；物理积分与请求分摊不重复相加。

## 7. 分阶段实施顺序

联合四格已经提供 B、C 单独贡献及交互：在固定 A 和同负载下，`Q11−Q10−Q01+Q00` 可描述质量交互；时延/资源用相应配对差和曲线。另做一次固定 token DAG 的 C 测量，把纯缓存收益与 B 改变阅读内容的收益分开。保留原登记的质量 +5 个百分点或等质量 P95 −15% 目标，同时明确完整在线资源变化。

模块目标、输入输出和验收明确后，子 agent 按不重叠文件范围实施；主 agent 负责 A→B→C 的共享状态、机制取舍与集成。训练/采集按上述依赖推进，不同时改变证据语义、阅读协议与收益标签。
