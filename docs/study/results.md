## 来源需求、前缀报价与容量回收

同一段材料可以位于多条 Native 前缀末尾。用 20 道 MultiDoc2Dial 开发题固定两段证据、历史和问题，依次预热 `[A,B]` 与 `[B]`，再让 agent 从 `[B,A]` 开始报价。只改变引擎目录，能报出完整 `[A,B]` 的题由 0 变为 20，实际采用该顺序的题由 1 变为 17。重访 prefill 从 4,451 降至 2,659 token，单 token 引擎 P95 从 167 降至 101 毫秒。自然结束时 F1 从 20.12 升至 21.40，重访引擎 P95 从 4.96 升至 5.19 秒。顺序和来源编号会影响生成长度。[同证据配对与执行量](../../results/kv_residency_20261122.json)

在 6 GiB 池中，固定 20 道 Loong 题各自的全部文档身份、可见片段和问题，分别切换目录与回收策略。下表为自然结束的重访请求，每组均评分 20/20。预热、报价与编译在计时区间之外。

与旧配置相比，联合配置在 18 题选择了完整前缀，19 题更快；评分 8 题提高、9 题持平、3 题下降。这批重访的 prefill 收益来自目录。更长的 Host 前缀可以比短的 GPU 前缀便宜。题目使用各文档首部均分的 6,144 个来源 token；分数变化包含证据顺序及引用编号的影响。[逐组开销与配对统计](../../results/kv_residency_20261122.json)

另一组实验固定 20 个真实多轮提示、请求顺序和每波四个长文干扰请求，分别提交上轮 agent 声明的来源需求和空需求。在 8 GiB 池内，旧策略在空需求下从 Host 搬回 6,208 token；按分配缺口回收后全部 GPU 命中。6 GiB 下同样避免了这 6,208 token 的搬运。4 GiB 下两种策略均要回收，保留真实需求使 GPU 命中从 0 增至 960 token。各组的 prefill 都是 9,785 token。8 GiB 空需求组重访前观察到的 GPU KV 用量峰值由 21,312 增至 23,808 token，活跃峰值保持 21,888。额外驻留的页仍可被分配器回收。[三档容量、实测回载与耗时](../../results/kv_residency_20261122.json)

最后直接干预闭环。20 题各预热两种完整顺序，在两次运行中仅交换 agent 向引擎声明的未来布局需求，再执行相同的四个冷前缀分配。6 GiB 下，只有按缺口回收、仍使用最近布局目录时，下一轮选材改变顺序 0/20 次。更新目录、保留原有主动降层时为 20/20 次；联合配置为 8/20 次。这 8 题中两种布局的 GPU 驻留优势都发生反转，agent 两次都选中了被声明的布局。其余 12 题仍选择同一顺序。还存在报价与执行之间的偏差。未来需求指向原顺序时，联合配置选中布局累计报出 56,832 个 GPU token，最终回执实际命中 10,944。该对照证实需求能够经由真实驻留影响下一轮选材，也量出了并发下单次报价的局限。[干预、报价及两侧物理回执](../../results/kv_residency_20261122.json)
