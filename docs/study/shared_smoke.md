# 信息、执行与缓存的联合决策：当前结果

本轮以“答案所需的新增信息”为决策对象：先复用已有事实，再选择证据和表示，最后按真实缓存获取成本安排执行。固定 Qwen3-32B，更新集合效用与停止头；四个 benchmark 各 20 题、公开参考历史、并发 4、种子 42。全部主比较行均完成 20/20。

## 机制与实现

| 环节 | 采用的机制 | 解决的问题 |
|---|---|---|
| 证据选择 | 查询相关性形成带依赖闭包的累计集合；一次比较新增信息、Need 满足度与完整获取费用 | 材料数量和向量幅值不再被直接当作质量收益 |
| 质量校准 | 借鉴 MMR 的相关性/新颖度分解，以真实答案差拟合 7 参数效用函数；重复材料不增加正向信息 | 简化效用模型，保留需求支持、互补信息与干扰惩罚 |
| 阅读与计算 | 先选材；原文能进入回答窗口则直接回答；完整字段绑定由 CPU 计算；需要分解时才读取 | 减少生成中间事实和再次归约；一次数值提取服务全部活动 Need |
| 预算 | 每次读取前预留系统、问题、历史、已有结论、正文份额和最终输出 | 已付读取费用不会继续挤掉全部终端空间；未完成总体保持观察状态 |
| 继续/停止 | 与选材共用 16 维信息摘要，加 12 维进度、成本和缓存状态；学习多步最终质量与费用 | 训练与运行使用同一状态和候选集合构造 |
| 缓存协同 | KV 驻留进入获取成本；已选材料可沿用 Native 已有前缀顺序；执行时选择 Native/InfoFlow | 缓存节省服务于证据获取，不给缓存材料额外语义分数 |
| 并发 | 独立编码工作线程合批，每个请求等待自己的 Future | 已完成请求不再继续替后来请求排空队列 |

集合训练使用 22/6 个训练/开发状态，共 142 个真实答案标签。最终 7 参数校准复用同批标签。停止头使用 11/4 状态、33 个答案标签，针对当前选择器重新采集。查询适配器、任务/字段头及两套共享骨干保持固定；生成模型没有训练。

## 基线与完整结果

普通文档问答为“问题 → 检索 → 常规拼接 → SGLang Native → 回答”。前三项质量乘以 100；Loong 为作者百分制。MT-RAG 使用作者生成指标的项目调和汇总；VersionQA 和 Loong 使用作者 rubric、固定 Qwen3-32B 裁判。完整响应包含检索、编码、排队、必要计算与回答。资源为批次驻留内存的时间积分，裁判费用在轻量 JSON 中单列。

前三项基线沿用相同题目、配置和未改变的 corpus passage 输入。Loong 共用文档分窗路径发生变化，因此两项参照已按当前代码重新运行。当前各组的题目 ID 集合已与共同清单核对。

## KV 协同的独立配对

同一道 MultiDoc2Dial 题、6 份相同证据、相同历史；每条分支清空缓存，以相同逆序文档预热。Native 两条分支的预热相同，InfoFlow 还建立独立块。单 token 输出用于分离预填充收益；耗时包含实际采用的报价、排序与编译。

| 路径 | 预热（ms） | 当前单 token 请求（ms） | GPU 命中 token | 实际 prefill token |
|---|---:|---:|---:|---:|
| Native，相关性原顺序 | 262.36 | 271.15 | 0 | 2378 |
| ContextKV，按缓存成本排列 | 266.57 | 44.01 | 2304 | 74 |
| 强制 InfoFlow 非前缀复用 | 768.23 | 506.26 | 2120 | 834 |

成本驱动排列实际选择 Native 精确路径，请求耗时下降 **83.8%**，prefill 减少 **96.9%**。这是 GPU 重访微配对，不是整批 P95；本轮未增加 Host 压力实验。

| 路径 | 完整回答（秒） | 输出 token | F1 |
|---|---:|---:|---:|
| Native，相关性原顺序 | 7.25 | 379 | 7.23 |
| ContextKV，按缓存成本排列 | 5.75 | 308 | 7.93 |
| 强制 InfoFlow 非前缀复用 | 26.40 | 678 | 3.52 |

完整回答长度不同，耗时差包含生成长度的影响。InfoFlow 在该请求上同时更慢、质量更低，不能由命中 token 数推断有效收益。对应可复用入口为 `python3 -m bench.cache_reuse`，命令见[运行手册](final_runbook.md)。

## 迭代结果与已付费用

本轮第一次迭代已接通选择前置和终端预算，但保留了原 MLP 集合校准；它仍倾向纳入过多材料。随后用新增信息与需求满足度的 7 参数函数替换，并重采停止标签。

| Benchmark | 第一次迭代质量 | 当前质量 | P95：第一次 → 当前（秒） | 输入 token：第一次 → 当前 |
|---|---:|---:|---:|---:|
| MultiDoc2Dial | 17.91 | 30.58 | 19.90 → 16.55 | 26471 → 8723 |
| MT-RAG | 59.15 | 57.91 | 63.90 → 41.03 | 163891 → 39946 |
| VersionQA | 80.00 | 80.00 | 51.63 → 40.63 | 155912 → 33842 |
| Loong | 33.25 | 26.50 | 189.56 → 131.11 | 563799 → 495062 |

更强的信息饱和改善了普通问答，但损害了 Loong 的完整证据选择。该退化保留在结果中，不以减少 token 抵消质量损失。

调度修复前的 MultiDoc2Dial 有一次传输 `ReadError`：19/20，完整分母 F1 为 30.40；单题补跑为 14.29。随后调度修复后的整批 20 题形成主比较行 30.58，未用单题结果拼接。失败批次、补跑、首次迭代和评分的已付费用全部保存在[轻量结果](../../results/mechanism-20261114.json)。

此前反复预算耗尽的财报分类题，本轮第一次迭代在 13927 输入、342 输出 token、25.19 秒内交付。输出仍将实际数值分入错误区间：预算衔接已改善，计算语义仍有缺口。

## 尚需改进的机制

1. **证据完整性与新颖度分开建模。** 相似措辞可能对应不同实体或总体成员，语义相似度不能独自判定冗余。当前有序集合也不能自由组合排名靠后的互补证据，Loong 质量下降暴露了这一边界。
2. **把明确区间分类编译为结构计算。** 现有 CPU 支持源字段筛选、连接与分组，但缺少问题定义的数值区间分组。正确读到数值后仍由生成模型分类，产生不必要的质量损失。
3. **控制辅助阶段和必需读取的总耗时。** MT-RAG、VersionQA 输入显著减少，完整 P95 仍高于基线，说明输入缩短没有解决全部关键路径。一次字段解码为 138 ms、对应整次证据编码为 1432 ms，单独优化解码不足以解释整体延迟。
4. **扩大价值校准的任务覆盖。** 当前集合与停止训练状态较少，对长文总体、互补证据和多步判断的校准仍弱。需要让标签表达实际缺失的信息及其答案价值。
5. **InfoFlow 需要足够大的可复用工作量。** 本次短请求的打分、独立块构建和重算成本超过节省；当前自动路径应依据实际总成本选择。

本轮只做了相关 CPU 检查、少量真实训练与上述端到端/缓存配对，未扩展测试套件。逐题答案、来源、训练资产保留在容器对应 `runs/current` 与 `data/training/shared`；仓库保存指标摘要，模型不外传。
