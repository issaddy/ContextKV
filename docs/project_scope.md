# ContextKV：场景、目标与模块职责

课题名称：**面向资源受限多轮文档问答的上下文管理与 KV 缓存协同优化研究**。

## 目标场景

面向依赖多份外部资料、上下文随交互增长与变化的多轮问答。适用任务包括公共服务咨询、产品支持、学术资料阅读、企业知识库及技术资料问答。用户会追问、比较、纠正条件、切换话题、回访旧材料；同一会话顺序执行，不同会话共享有限的 GPU/Host 资源。

多轮准确性包括：理解指代和省略，承接对象与条件，让用户纠正及时生效，切换任务后更新假设，回访时找回适用来源。历史回答提供对话背景，外部资料支持事实结论；部分可答时先完成有依据的部分，再说明缺失信息。

例如，用户从“这个项目如何申请”追问“我是在校生呢”“换到另一地区呢”，随后回访先前地区的材料要求。系统需要同时维护任务、地区与人群条件，组织当前证据，并复用仍然适用的上下文。

代表性资料序列为 `{A,B} → {B,C} → {C,D}`。每轮紧凑重建会损失部分缓存前缀，持续追加则增加旧材料、注意力计算和 KV 占用。文本重建之后，旧分支的引用保护也需要更新。这三个问题构成 A/B/C 的协同主线。

验证围绕以下交互与负载展开，分别说明已覆盖的范围：

| 场景特征 | 系统需要做到 | 验证重点 |
|---|---|---|
| 多资料互补、比较或条件分支 | 找齐必要信息，区分来源适用范围并完成各项需求 | 必要回答点、条件/例外和实际原文支持 |
| 连续追问、纠正、话题切换与回访 | 更新当前任务，保留仍适用的条件，恢复被回访的资料 | 实际生成历史下的完整会话质量 |
| 长资料与持续增长的历史 | 在窗口和资源预算内保留必要背景，控制冗余材料 | 实际输入长度分层、回答完整性及完整响应 |
| 检索材料更换与来源版本更新 | 区分仍可复用和已失效的证据及KV引用 | 材料集合变化、版本变化分别验证 |
| 多会话并发、停顿与回访 | 在共享GPU/Host约束下提供有效服务 | 非截断达标吞吐、等待、资源积分与恢复成本 |

公开问答任务与系统负载共同覆盖这些特征。单轮长文任务可补充原文阅读能力，短会话可诊断承接错误；各自的结论限定在实际覆盖的场景。不能将某一类样本的表现直接推广到完整目标场景。

## 研究目标与指标

**优先提高目标任务回答质量，在此基础上改善完整响应、服务能力和资源效率。** 方法可以直接复用成熟工作，也可以组合、替换或扩展，优先级由实际应用收益决定。

| 方面 | 评价内容 | 主要指标 |
|---|---|---|
| 回答质量 | 当前任务与对象正确，条件/版本适用，必要信息完整，有来源支持；多轮纠正与回访有效 | 任务正确率、完成率或官方参考答案/来源评分；按任务类型和会话汇总 |
| 响应性能 | 用户收到完整回答所需时间及连续多轮等待 | 完整响应均值/P95、会话累计等待；流式交付时增加 TTFT/TPOT |
| 服务能力 | 给定设备、缓存预算和服务时限下的有效完成能力 | 非截断时延达标吞吐、稳定到达率或并发能力 |
| 资源效率 | 生成、解释、检索及缓存保留的完整资源代价 | GPU/Host 唯一 KV 槽位积分/完成轮，辅助模型驻留与调用成本 |
| 工程可靠性 | 可运行、状态一致、可恢复、可复现 | 失败/截断/未完成轮次及提交恢复检查 |

当前 HTTP 接口完整返回，以完整响应时间评价交互体验。引擎 TTFT、输入长度、缓存命中率、追加比例、检索召回和控制开销用于解释系统表现。具体评分、分母、缺失值和各版本结果集中在[数据与评价](data_and_evaluation.md)。

比较使用共同的基座模型、资料范围、问题、输出要求及资源口径。系统对照允许各方法组织不同证据，检验 A/B/C 的整体效果；隔离 B/C 时共享实际输入材料。质量收益及其成本、同质量下的加速、同预算下的服务能力提升，都属于有应用价值的结果。质量要求与服务时限按实际场景设定。

## 模型边界与机制归因

课题研究可迁移的任务/条件承接、证据组织、上下文装配与KV管理机制，不以特定模型规模或“大模型规划、小模型回答”的分工作为机制前提。模型承担可替换的语义与生成能力；模型身份、分词、上下文窗口和缓存格式仍需由工程接口明确绑定，成本参数按实际后端标定。

效果不是与模型无关的常数。机制比较首先固定生成模型、采样、资料与资源条件，辅助能力及全部调用成本显式列出并做消融；不能把换用更强模型或增加调用得到的收益直接归为上下文/KV机制收益。需要时再跨模型检查方向是否可迁移。当前8B生成、32B解释属于已记录的部署配置，其必要性仍受质量和完整成本验证约束，不是课题固定架构。

后续优先比较信息表示、原文结构与依赖、需求覆盖、证据更新、布局复用及资源决策等方法。可复用相关论文中的思想或实现，但须区分通用机制、训练依赖和额外在线模型计算，并在本课题场景中验证。

## 实现过程中的纠偏

每轮改进先明确目标场景中的失败现象、共同根因和拟改变的机制，再选择可复用方法及验证范围。持续存在的瓶颈应扩大相关方法、论文与实现的比较，检查表示、算法、系统协同及评测覆盖是否合适，避免只在局部提示或少量样本上反复调整。

保留方案的依据是实际回答收益及完整成本，而不是中间指标、有效格式或代码复杂度。检索、缓存和工程正确性检查分别解释机制，不替代应用效果。无效、重复或过时实现及时移除，保留可追溯实验记录。A/B/C的划分服务于应用目标，必要时可以调整职责和算法，不为了维持既有实现而缩小目标。

## 模块职责

| 模块 | 主要工作 | 输出 |
|---|---|---|
| A：任务、证据与上下文 | 多轮任务状态与条件更新；检索、重排、来源和依赖组织；从共同材料构造追加与重建候选 | 当前任务、适用证据、完整消息与 token IDs、引用范围、候选可行性 |
| B：实际成本决策 | 读取同批原生 GPU/Host 缓存状态；估计等待、传输、Prefill、Decode 和控制成本；选择执行方案 | 动作、成本分项、估计适用范围及选择原因 |
| C：KV 生命周期 | 将业务 epoch 映射为原生会话引用；提交新状态后退役旧引用；处理共享、响应丢失与重启 | 一次提交的回答和账本、当前 epoch、退役记录与资源观测 |

`问题＋实际历史 → 任务/检索/证据组织 → A 候选 → 原生报价 → B 选择 → SGLang 生成 → C 提交和退役 → 成本与资源反馈`

A 的两个候选使用共同的当前证据和完整实际问答；B 选择预计完整成本较低者，误差带用于描述预测差异，平局结合原生工作集和输入长度；成本模型覆盖范围之外使用配置的固定策略。C 在新结果持久提交后解除旧引用，由 SGLang 执行物理分配、传输和淘汰。接口与恢复状态详见[架构](architecture.md)。

## 工程与研究范围

现有实现基于 Qwen3-8B/32B 和固定 SGLang，支持 CLI/HTTP、自动检索、多会话、事务提交、幂等和恢复。当前部署为单机，每个生成/解释实例各使用一张 GPU；8B 成本表对应 H200、16384 GPU KV 槽和 54272 Host KV 槽。使用其他资源配置时按其实际运行条件装配。

统一评测复用 MT-RAG、MultiDoc2Dial 和 MTRAG-UN。长上下文、版本演化或资源竞争的覆盖不足时，可补充合适的公开任务或完整场景集。验证规模由需要解决的问题决定，优先复用已有答案和观测。

研发围绕实际瓶颈推进：分析任务与来源、理解机制、实现协同、针对性验证。检索、证据选择、调度、成本学习、压缩和模型适配均可作为改进手段。训练工具是可选离线能力，正常服务直接使用已有模型。
