# ContextKV：课题场景、目标与模块职责

2026-10-24。本文依据原技术方案、当前代码和已有结果重新对齐课题主线。后续任务排序以本文及[模块现状](implementation_plan.md)为准；旧实验清单和研究支线不自动成为交付前置。研究路线可以扩展，但必须服务于这里的场景问题。

## 1. 研究什么场景

**有限 GPU/Host KV 容量的单机，为多个用户提供连续的企业技术文档问答。** 用户会追问配置、参数、版本差异、适用条件和排障步骤。同一会话按顺序提交，不同会话并发；轮间有停顿。每轮检索证据可能新增、重叠、回访或更新。

代表性证据序列为 `{A,B} → {B,C} → {C,D}`。系统面临三个耦合问题：

1. 每轮重建“完整实际问答历史＋当前必需证据”，输入较紧凑，但移除或重排证据可能破坏可复用前缀。
2. 沿已执行的上下文追加新问题和缺失证据，有机会复用更多 KV，但累积旧材料会增加注意力、Decode 和缓存占用，也可能干扰回答。
3. 文本重建后，旧缓存分支可能仍被会话引用保护。文本变短不等于物理占用下降；其他会话的竞争、Host 淘汰和传输又会改变下一轮取舍。

**课题要协调“给模型什么上下文、当前选择哪个上下文、旧上下文的缓存何时解除保留”。** 目标不是单独提高缓存命中率、减少输入 token，或训练一个新的问答模型。

主要负载应体现真实多轮技术问答及合理的并发、回访和资源压力。已有 MTRAG 技术文档负载可复用，但自然会话长度不等于天然超长会话；不得无限追加材料、极端缩小 KV 池来制造优势。Doc2Dial 等材料可辅助研究条件/对话行为，不能替代目标技术场景的系统验收。

## 2. 系统目标和约束

在共同模型、检索材料和资源预算下，联合评价：

| 方面 | 需要取得的效果 | 不能替代它的局部指标 |
|---|---|---|
| 回答质量 | 保留必要证据和真实历史；范围、条件、版本及引用正确，回答有用且覆盖需求；优化不得造成不可接受的退化 | 引用编号合法、命中原文、检索召回高、训练 loss 下降 |
| 系统性能 | 改善完整响应时间，并报告 TTFT、TPOT、排队及满足 SLO 的有效吞吐 | 只看 Prefill 或单个最快请求 |
| 资源效率 | 在给定 GPU/Host 预算下减少无效保留、传输、淘汰和重算，支持合理多会话负载 | 命中率高、逻辑上下文短、退役 ACK 数量多 |
| 工程可靠性 | 状态一致、失败可解释、结果可恢复、可运行和可复现，控制开销与维护复杂度合理 | 测试数量、文档数量或功能开关数量 |

回答质量既是约束，也是可改进的目标。先与**同一基座**的强基线比较，判断上下文/KV 机制引入的增益或损失；不把解决基座全部通用回答错误当作系统交付前置。质量容忍界限、SLO 和资源预算应按具体负载预先确定，不依据观察结果放宽。

当前采用已有 Qwen3-8B/32B、固定 SGLang、单 GPU、BF16、GPU＋Host 两层缓存。Qwen2.5-7B 永久退役。保留完整已提交的用户问题与实际答案；不偷偷截断/摘要历史、替换为标准答案或隐藏额外模型调用。预算不足须明确处理；历史压缩或模型适配是可研究的扩展，不是当前默认行为。

## 3. A/B/C 各自需要完成什么

| 模块 | 核心职责 | 输入与输出 | 当前最需要补足 |
|---|---|---|---|
| **A：证据与上下文组织** | 管理证据身份、版本、来源、当前可见性与明确依赖；基于同一已提交快照构造正确的 APPEND/REBUILD | 输入：当前问题、共同检索结果、完整实际 QA、执行账本。输出：两个候选的完整消息/真实 token IDs、必需与可见证据、引用位置、可行性 | 在目标负载中确认候选既保留必要材料，又有有价值的复用/紧凑性取舍；处理实际来源范围、旧版本和材料组织问题 |
| **B：实际成本感知决策** | 根据真实缓存驻留和执行成本选择候选，避免节省 Prefill 却增加更多 Decode/控制成本 | 输入：A 候选、同批只读 GPU/Host ready/pending 报价、当前资源/调度观测、适用本模型配置的成本模型及过去统计。输出：选中动作、分项估计、不确定性、选择/回退原因 | 建立当前 Qwen3 有效范围内的必要标定并接入决策；验证它相对强简单策略的整体净收益，不能用旧模型成本表或三对诊断结果代替 |
| **C：上下文版本与 KV 生命周期** | 将业务上下文版本正确映射到原生缓存会话引用，协调提交、退役和恢复，并观察实际资源后果 | 输入：选中动作、epoch/generation/restart、实际输出/receipt、成功或失败事件。输出：成功一次提交的 QA/账本、新当前 epoch、旧引用退役 outbox/ACK、资源遥测 | 在有限资源、多会话竞争和回访中验证保留/解除保留的收益及重算代价，处理真实接线问题；退役 ACK 不能冒充物理释放 |

**A 的关键不变量：**“归档过”“见过”和“当前候选实际可见”不同。APPEND 只能省略仍在实际输入中的正确版本正文；REBUILD 从完整实际 QA 和共同必需证据重建。两个候选构造不修改已提交状态，也不能用不同当前证据制造比较优势。真实 token 前缀由固定模板和引擎决定，文本看似追加不保证全部 KV 可复用。

**B 的关键不变量：**先满足证据、版本、预算等可行性约束，再比较成本。使用未来答案长度或质量标签属于泄漏；在线只可用提交前信息和已完成历史。报价不是资源预留；缺标定、超支持域或观测不可用时使用明确简单回退，不伪造准确成本。排队、传输、Prefill、Decode 和控制时间按实际测量边界计入，不能重复累加。

**C 的关键不变量：**APPEND 通常沿用当前 epoch，REBUILD 建立新 epoch；成功生成并持久提交后，才退役被替代引用。响应丢失、提交失败、退役失败及引擎重启按已有恢复协议处理。SGLang 继续拥有物理缓存匹配、分配、锁、传输、准入和淘汰；不另建影子缓存或调度器。会话引用只是保留机制，不是物理块所有权。

## 4. 三个模块怎样协同

`问题＋真实历史 → 共同检索/证据集合 → A 构造候选 → 原生只读报价 → B 选计划 → SGLang 原生生成 → C 提交新状态/退役旧引用 → 实际成本与资源反馈`

HTTP/CLI、检索适配器、SQLite、可观测性、故障恢复和评测是这条链的工程支撑，不需要各自变成独立研究课题。固定策略也可走完整链；复杂策略应证明收益后再进入默认配置。

每项局部改进都必须回答跨模块问题：A 的前缀稳定是否被长输入 Decode 抵消？B 的选择是否考虑 C 解除保留后的后续重算？C 的资源保护是否挤压其他会话？总收益是否足以覆盖控制、检索和额外模型调用成本？

## 5. 当前状态与正确的推进顺序

现有 `controller/service.py`、`candidates.py`、`planner.py`、`epoch.py`、Session Store 和固定引擎补丁已经打通主流程。已有 HTTP/CLI、检索、提交/恢复和有限 Qwen3 真机验证，**无需重新搭建一套系统**。但当前可用 Qwen3 示例以 `always_rebuild` 为主；代码存在不等于 B/C 的真实净收益已建立。

接下来依次推进：

1. **收束一个当前可运行的主线版本。** 统一现有 Qwen3 配置、真实多轮目标负载、检索/证据策略、控制器与原生执行、结果导出；只修实际缺口。已有正确性检查通过的部分不反复重做。
2. **补齐直接决定 A/B/C 效果的空白。** 先利用已有候选、执行和质量结果定位有价值的取舍；完善当前模型的必要成本支持和显式回退，将版本生命周期与真实资源观测共同接入。没有收益空间时简化机制，而不是为覆盖率扩大实验。
3. **做一次范围明确的系统闭环比较。** 与同基座的正常 RAG＋原生前缀缓存、原生会话/HiCache及强简单策略比较，使用相同材料、预算和真实历史；同时保留质量、完整时延、资源和失败分母。先小规模诊断，只有关键结论才扩大独立验证/消融。
4. **保留有净收益的机制并形成交付。** 输出可运行配置、模块接口、必要标定、复现实验和带适用边界的结论。允许某个复杂机制不优于简单方案，不以无限探索推迟集成。

当前尚未完成的是共同目标负载上的系统联合验收、Qwen3 成本决策有效性和有限资源下生命周期净收益。不能用更多格式测试、通用问答数据审阅或微调接口代替这些结果。

## 6. 贡献与扩展如何保持对齐

可形成贡献的主线为：**版本与可见性感知的上下文组织；真实缓存状态与完整执行成本驱动的选择；业务上下文版本和原生缓存生命周期的协同机制。** 这些是待证实的贡献方向，不把已有实现直接写成优胜结论，也不把 SGLang 本来就有的缓存能力算成原创。

继续复用已核对的 ContextPilot/TokenPilot 组织思想、成熟检索/重排、SGLang Radix/HiCache 与会话软引用、标准成本拟合和在线决策方法；具体复用、修改点及证据分别记录在[贡献说明](research_contributions.md)、[架构](architecture.md)和[验证记录](verification.md)。不因论文名称增加模块，先理解适用条件和运行代价。

不限制以后从检索、证据选择、调度、成本学习、压缩或模型适配提出改进。但新增方向应先明确：它解决哪个已观察到的核心瓶颈、怎样与现有机制协同、带来多少额外成本、如何在共同基线下判断价值。

**训练目前是暂缓扩展的可选支线。** 已完成的 30-step Qwen3-8B 小规模训练与 CPU 合并产物保留，不表示质量改善；已准备的 32 次对比生成没有执行。当前不扩大训练、teacher 或专门训练评测，把资源回到上述主线。训练将来可以有价值，但不是课题实现、创新或验收的必要条件。
