# ContextKV：课题场景、目标与模块职责

2026-10-27。本文依据原技术方案、当前代码和已有结果明确课题场景、目标及指标适用性。后续任务排序以本文及[模块现状](implementation_plan.md)为准；旧实验清单和研究支线不自动成为交付前置。研究路线可以扩展，但必须服务于这里的场景问题。

## 1. 研究什么场景

**面向依赖外部资料、需要承接真实会话历史、证据随交互变化的多轮文档与知识问答，在有限 GPU/Host KV 资源下服务多个会话。** 场景包括公共服务与政策咨询、产品与使用支持、学术资料问答、企业知识库及技术文档问答等。用户可能追问、比较、澄清条件、切换话题或回访先前材料；每轮证据可能新增、重叠、回访或更新。同一会话按顺序提交，不同会话并发，轮间允许停顿。当前生成服务以单机、单个生成 GPU 为交付范围；检索组件所用 CPU 或独立 GPU 按实际配置计入系统说明。应用领域不限定为企业或技术文档。

“多轮更精准”首先指当前问题与历史的关系处理正确：解析指代和省略，承接已经明确的对象与条件，接受用户纠正，在话题/版本切换后撤销不再适用的假设，回访时找回正确来源。历史回答用于理解对话，不能自动成为事实证据。重点改进会话理解、检索、证据选择及上下文组织造成的质量问题，并保留有依据的部分、明确缺失部分。

例如，一段公共服务咨询可以从“这个项目如何申请”转到“我是在校生呢”“换到另一地区呢”，再回访“回到刚才的地区，需要哪些材料”。系统必须随对象、地区和条件变化调整证据，同时复用仍然适用的内容。这里的例子描述任务结构，不假定任何具体政策规则。

课题边界按任务结构定义：回答依赖可追溯的外部材料，历史与证据随轮次演化，上下文组织会影响 KV 复用和执行成本，多会话共享有限资源。不同领域复用同一套机制，通过语料、检索和评价适配接入；不为每个领域另造系统。上述应用是适用方向，不表示已经逐一完成有效性验证。

代表性证据序列为 `{A,B} → {B,C} → {C,D}`。系统面临三个耦合问题：

1. 每轮重建“完整实际问答历史＋当前必需证据”，输入较紧凑，但移除或重排证据可能破坏可复用前缀。
2. 沿已执行的上下文追加新问题和缺失证据，有机会复用更多 KV，但累积旧材料会增加注意力、Decode 和缓存占用，也可能干扰回答。
3. 文本重建后，旧缓存分支可能仍被会话引用保护。文本变短不等于物理占用下降；其他会话的竞争、Host 淘汰和传输又会改变下一轮取舍。

**课题要协调“给模型什么上下文、当前选择哪个上下文、旧上下文的缓存何时解除保留”。** 目标不是单独提高缓存命中率、减少输入 token，或训练一个新的问答模型。

主benchmark统一采用公开MT-RAG任务，MTRAG-UN补充歧义、依赖历史与可答性挑战；自构问题只作缺陷复现。固定公布版本与实际发布范围见[评价](data_and_evaluation.md)。主要负载应体现真实多轮文档与知识问答及合理的并发、回访和资源压力。已有 MTRAG、Doc2Dial 等材料按其任务结构和标注能力复用，技术文档只是其中一个验证实例；Doc2Dial 可用于文档支撑的服务咨询与条件澄清，系统验收仍需实际生成历史及完整执行链。负载覆盖依据证据重叠、话题切换、回访、条件/版本变化和并发工作集选择，不按行业机械扩充实验矩阵。自然会话长度不等于天然超长会话，不得无限追加材料、极端缩小 KV 池来制造优势；跨领域适用性与已有实测范围分别报告。

## 2. 系统目标和约束

**研究目标：面向动态证据的多轮问答，联合优化会话所需上下文、执行策略和原生 KV 生命周期，在保持或提高目标任务回答有效性的同时，改善有限资源下的完整响应、服务能力或资源效率。**

回答有效性指完成用户当前及连续追问的实际任务：对象与任务承接正确、纠正生效、有效条件/版本保持、必要内容有依据且完整。A 负责这种上下文与证据组织，B 选择追加或重建，C 协调成功提交后的缓存引用保留与退役。实现手段可以复用、组合或扩展现有工作；目标不以某个算法名称、某个动作比例或必须原创某种组件来定义。

在共同基座模型、资料库、用户问题、输出要求和资源预算下，联合评价：

| 方面 | 需要取得的效果 | 不能替代它的局部指标 |
|---|---|---|
| 目标任务质量 | 正确承接多轮指代、纠正与条件切换；保留必要证据和真实历史；回答覆盖任务所需内容，适用对象/条件/版本正确且有来源支持；优化不得造成不可接受的退化 | 引用编号合法、固定措辞匹配、检索召回高、训练 loss 下降 |
| 系统性能 | 按实际返回方式改善交互延迟、完整响应和满足 SLO 的服务能力 | 只看 Prefill 或单个最快请求 |
| 资源效率 | 在给定 GPU/Host 预算下减少无效保留、传输、淘汰和重算，支持合理多会话负载 | 命中率高、逻辑上下文短、退役 ACK 数量多 |
| 工程可靠性 | 状态一致、失败可解释、结果可恢复、可运行和可复现，控制开销与维护复杂度合理 | 测试数量、文档数量或功能开关数量 |

回答质量既是约束，也是可改进的目标。先与**同一基座**的强基线比较，判断上下文/KV 机制引入的增益或损失；不把解决基座全部通用回答错误当作系统交付前置。质量容忍界限、SLO 和资源预算应按具体负载预先确定，不依据观察结果放宽。

当前采用已有 Qwen3-8B/32B、固定 SGLang、单 GPU、BF16、GPU＋Host 两层缓存。Qwen2.5-7B 永久退役。保留完整已提交的用户问题与实际答案；不偷偷截断/摘要历史、替换为标准答案或隐藏额外模型调用。预算不足须明确处理；历史压缩或模型适配是可研究的扩展，不是当前默认行为。

### 核心指标与判断方式

主评价只保留以下四组。它们对应用户回答需求、交互等待、多会话承载和有限资源约束；不把局部缓存指标混进总分。

| 主评价 | 固定口径 | 实际用途 |
|---|---|---|
| 目标任务质量 | 按任务所需信息评价回答正确性与覆盖，单列指代/任务继承、纠正、条件/版本切换、回访子集；评价关键结论的来源支持和部分可答处理；任务要求引用时评价引用正确性与覆盖 | 采用适合任务标注的正确率、完成率或分项评分，说明分母并按会话汇总；已有五维分数只是可用工具，不自动成为所有任务都要通过的统一门槛 |
| 响应延迟 | 完整响应的会话等权均值、请求P95、会话累计系统等待；真正流式交付时另看TTFT P50/P95和TPOT P95 | 当前HTTP完整返回，以完整响应为主；内部引擎首字时间只作诊断。累计系统等待不含用户think time |
| 服务能力 | 相同资源、预先声明返回方式和SLO下的非截断时延达标吞吐；有相应负载验证时才报告最大稳定到达率/并发 | 与质量结果共同判断服务能力；单个低负载点不能说明最大容量 |
| 资源效率 | 已观测运行区间的GPU/Host唯一KV槽位积分，按非截断完成轮次归一；需要时比较同质量/同SLO所需资源预算 | KV占用应与完成服务量一起解释；多保留有效缓存也可能有收益，峰值占满不等于低效 |

质量评价优先复用数据集已有的任务标注与正确性/覆盖评分。需要补充多轮指标时，“多轮关系处理正确率”的分母是实际包含指代、纠正、条件切换或回访的轮次，判据是最终回答是否正确使用相应对象、任务与条件，不是中间改写是否匹配某一句参考文本。“任务完成率”依据预先列明的必要回答点及可答范围判断，不能用 HTTP 成功率代替；缺少任务标注时报告已有分项证据，不补造完成率。

**工程验收项：**失败、超时、截断、未完成后续轮次、提交/恢复一致性以及引用可见性/范围违规单列。它们不与速度任意加权；也不把所有成功HTTP请求称为合格答案。

报告使用指标版本2：当前默认`response_mode=buffered`。缓冲返回必须预先声明`complete_seconds`才能计算goodput；缺省保留“未配置”。实际流式交付显式声明`response_mode=streaming`，使用TTFT/TPOT门槛，可同时约束完整响应。时延达标分子排除失败、截断、输出为空和缺少终态证据的请求，质量仍单独评价。指标声明用于选择已有观测口径，不会使缓冲API变成流式API。

**机制诊断只用于解释主结果：**A的输入长度、真实公共前缀、证据保留及检索Recall/nDCG；B的控制开销、成本误差、选择/回退原因；C的GPU命中、Host恢复、实际Prefill、完成H2D/D2H、淘汰与重算。保留现有原始字段，不把追加比例、命中率、压缩率、退役次数、tokens/s或训练loss列为课题最终成败指标。P99仅在样本规模足够且结论需要时使用，不作为小批次主表项目。

完整系统比较固定模型、资料库、用户问题、输出要求和资源，允许会话理解、检索及证据组织方法产生不同的本轮证据，以检验 A 对多轮精准性的作用；必须记录证据差异及其成本。隔离 B/C 效果时共享检索与必需证据，防止将检索差异误归为缓存收益。两类比较都区分稳定追问、证据切换、回访和真实资源竞争。P3计入检索，P2从给定证据就绪计时；已有结果优先复用，不为补满指标启动额外矩阵。

不要求所有指标同时改善。质量及资源预算满足既定要求后，**相同预算更快完成、相同预算服务更多请求、或更少资源达到同等服务水平**均可形成有价值的结论；改善质量而保持合理成本也属于课题收益。具体收益与代价一起报告，不随意加权为总分，也不预设未经测量的提升百分比。

### 指标适用性与成效判定

按负载实际包含的历史依赖、证据演化和资源竞争解释结果。质量改善可以伴随合理的额外等待；延迟改善也不要求峰值显存同时下降。引用格式、篇幅、改写句式只在影响当前任务或追溯时评价；致谢等普通对话无需拒答或凑引用。具体benchmark口径统一见[数据与评价](data_and_evaluation.md)。

任务错误全部保留，再区分共同基座错误、本系统新增或放大的错误、尚未明确的归因。解决所有通用回答错误不是交付前置，已有正面结果也不会被个别开发案例抹去。B的回退与实际成本选择、C的引用退役与物理资源后果分别记录；未覆盖竞争或回访的负载不用于判断相应资源机制。

模型、任务、资源、质量容忍度和服务要求在比较前约定。先完成共同公开负载与强原生基线的整体比较，再按关键不确定性补充消融；已有答案和观测优先复用，独立冻结测试用于支撑重要结论。指标或验证步骤不因与任务无关而成为研发门槛。

方法可以直接复用成熟工作，也可以组合、替换或扩展。来源用于引用、许可和复现；优先级由应用收益决定。实际净收益包含选择误差、控制、上下文增长与资源竞争，所有策略均可按证据改进。

## 3. A/B/C 各自需要完成什么

| 模块 | 核心职责 | 输入与输出 | 当前最需要补足 |
|---|---|---|---|
| **A：证据与上下文组织** | 利用真实历史形成适合当前问题的检索与证据上下文；管理身份、版本、来源、可见性与依赖；基于同一快照构造 APPEND/REBUILD | 输入：当前问题、检索材料、完整实际 QA、执行账本。输出：检索/证据组织结果及两个候选的完整消息/真实 token IDs、必需与可见证据、引用位置、可行性 | 补齐跨轮指代、纠正与条件切换的实际准确性；确认保留必要材料并存在有价值的复用/紧凑性取舍；避免将引用资格当作语义支持 |
| **B：实际成本感知决策** | 根据真实缓存驻留和执行成本选择候选，避免节省 Prefill 却增加更多 Decode/控制成本 | 输入：A 候选、同批只读 GPU/Host ready/pending 报价、当前资源/调度观测、适用本模型配置的成本模型及过去统计。输出：选中动作、分项估计、不确定性、选择/回退原因 | 当前 Qwen3 必要标定已接通，追加偏好修正已有一次联合运行收益；继续降低控制开销并完善相对原生的整体效果 |
| **C：上下文版本与 KV 生命周期** | 将业务上下文版本正确映射到原生缓存会话引用，协调提交、退役和恢复，并观察实际资源后果 | 输入：选中动作、epoch/generation/restart、实际输出/receipt、成功或失败事件。输出：成功一次提交的 QA/账本、新当前 epoch、旧引用退役 outbox/ACK、资源遥测 | 在有限资源、多会话竞争和回访中验证保留/解除保留的收益及重算代价，处理真实接线问题；退役 ACK 不能冒充物理释放 |

**A 的关键不变量：**“归档过”“见过”和“当前候选实际可见”不同。APPEND 只能省略仍在实际输入中的正确版本正文；REBUILD 从完整实际 QA 和共同必需证据重建。两个候选构造不修改已提交状态，也不能用不同当前证据制造比较优势。真实 token 前缀由固定模板和引擎决定，文本看似追加不保证全部 KV 可复用。

**B 的关键不变量：**先满足证据、版本、预算等可行性约束，再比较成本。使用未来答案长度或质量标签属于泄漏；在线只可用提交前信息和已完成历史。报价不是资源预留；缺标定、超支持域或观测不可用时使用明确简单回退，不伪造准确成本。排队、传输、Prefill、Decode 和控制时间按实际测量边界计入，不能重复累加。

当前按`C_APPEND−C_REBUILD`的方向选择预计完整成本较低者，误差带仅解释预测差异，默认无固定轮数冷却。平局时使用有效的原生输入需求观测，否则按共同输入长度排序；原生预算与预计服务长度分别计算，最终准入仍由引擎负责。完整公式、支持范围和取舍统一见[联合问题建模](research/joint_optimization_model.md)。

**C 的关键不变量：**APPEND 通常沿用当前 epoch，REBUILD 建立新 epoch；成功生成并持久提交后，才退役被替代引用。响应丢失、提交失败、退役失败及引擎重启按已有恢复协议处理。SGLang 继续拥有物理缓存匹配、分配、锁、传输、准入和淘汰；不另建影子缓存或调度器。会话引用只是保留机制，不是物理块所有权。

## 4. 三个模块怎样协同

`问题＋真实历史 → 共同检索/证据集合 → A 构造候选 → 原生只读报价 → B 选计划 → SGLang 原生生成 → C 提交新状态/退役旧引用 → 实际成本与资源反馈`

HTTP/CLI、检索适配器、SQLite、可观测性、故障恢复和评测是这条链的工程支撑，不需要各自变成独立研究课题。固定策略也可走完整链；复杂策略应证明收益后再进入默认配置。

每项局部改进都必须回答跨模块问题：A 的前缀稳定是否被长输入 Decode 抵消？B 的选择是否考虑 C 解除保留后的后续重算？C 的资源保护是否挤压其他会话？总收益是否足以覆盖控制、检索和额外模型调用成本？

## 5. 当前状态与正确的推进顺序

现有 `controller/service.py`、`candidates.py`、`planner.py`、`epoch.py`、Session Store 和固定引擎补丁已经打通主流程。已有 HTTP/CLI、检索、提交/恢复，当前 Qwen3 阶段成本与 A/B/C 已联合执行，**无需重新搭建一套系统**。通用示例保留 `always_rebuild`，实测成本配置位于 `configs/qwen3_8b_cost.yaml`。早期P3开发负载曾观测到响应收益；最新固定公开比较已完成492次回答，尚未体现净提速，质量评分进行中。多轮找回有效来源的收益、对象误判和旧回答错误延续均保留，具体结果见评价说明。

具体工作顺序只维护在[当前实现清单](implementation_plan.md)，本文不另列阶段计划。`guides/` 是使用说明，`research/` 是现有机制参考；旧计划和逐轮纪要已从当前文档树移除。

当前工程与开发对照已完成，整体质量非劣与性能优胜仍需独立证据。机制实现、局部收益和广泛优胜是不同层次的结论。

## 6. 贡献与扩展如何保持对齐

可形成贡献的主线为：**版本与可见性感知的上下文组织；真实缓存状态与完整执行成本驱动的选择；业务上下文版本和原生缓存生命周期的协同机制。** 这些是待证实的贡献方向，不把已有实现直接写成优胜结论，也不把 SGLang 本来就有的缓存能力算成原创。

继续复用已核对的 ContextPilot/TokenPilot 组织思想、成熟检索/重排、SGLang Radix/HiCache 与会话软引用、标准成本拟合和在线决策方法；具体复用、修改点及证据分别记录在[贡献说明](research_contributions.md)、[架构](architecture.md)和[数据与评价](data_and_evaluation.md)。不因论文名称增加模块，先理解适用条件和运行代价。

不限制以后从检索、证据选择、调度、成本学习、压缩或模型适配提出改进。但新增方向应先明确：它解决哪个已观察到的核心瓶颈、怎样与现有机制协同、带来多少额外成本、如何在共同基线下判断价值。

**训练是暂缓扩展的可选支线。** 已有通用工具和产物保留，当前不扩大训练、teacher 或专门训练评测；它们不是 A/B/C 运行和交付的前置。
