# 统一 benchmark、指标与已有结果

主线采用统一运行入口、场景覆盖和质量/完整成本口径，优先使用公开任务与原始资料。公开数据仍缺少的重要场景可以补建完整benchmark；工程回归小例子与系统评测分别报告。统一不意味着把不同任务的分数或协议混成一个总分。

## 公开 benchmark 的选择

| Benchmark | 与课题的关系 | 当前用法 |
|---|---|---|
| [MT-RAG](https://github.com/IBM/mt-rag-benchmark) | 110个人工多轮会话、842个任务，覆盖Wikipedia、金融、政府与技术资料 | 统一主benchmark；固定原问题、来源、参考答案和会话顺序，运行P1/P2/P3 |
| [MTRAG-UN](https://github.com/IBM/mt-rag-benchmark/tree/main/mtragun-human) | 非独立问句、歧义、不可答/部分可答和回答澄清 | 官方挑战补充，使用选定轮次的P1历史，不伪造前序任务或改成新的完整会话 |
| [MultiDoc2Dial](https://github.com/IBM/multidoc2dial) | 跨文档、跨主题的目标导向对话，含文档结构 | 已接通原validation/test共1322会话、8762个系统问答轮和全部488文档；P3采用实际生成历史，参见[接口与分组协议](guides/doc2dial.md) |
| [ChatRAG-Bench](https://huggingface.co/datasets/nvidia/ChatRAG-Bench) | 将Doc2Dial、QReCC、TopiOCQA、INSCIT等10种任务整合为会话问答套件，含文本/表格/不可答情况 | 可直接补充给定历史下的跨任务质量；上下文准备与评分按上游协议，不当成自然演化的KV性能轨迹。本轮已核对数据格式/官方评分接口，未运行模型 |
| [CORAL](https://github.com/RUC-NLPIR/CORAL) | 8000个自动构建的Wikipedia多轮会话，含跨主题、长回答和引用标注 | 可补充开放领域知识密集问答；已有公开数据和代码，按作者分区/指标使用。已审阅论文与数据格式，尚未接入运行 |
| [Loong](https://github.com/MozerWang/Loong) | 中英长文本多资料定位、比较、聚合及推理；每项材料有任务作用 | 优先的长上下文质量补充；按原长度分层与当前模型支持范围选用，不以填充噪声制造长输入。它是单次多文档任务，不替代多轮链路 |
| [LongTableBench](https://aclanthology.org/2025.findings-emnlp.638/) | 长表格、多表与多轮推理 | 表格机制确有需求时启用，避免将专门表格评分强加到普通文档QA |
| [TurnFlow](https://aclanthology.org/2026.findings-emnlp.825/) | 2026年公开研究中的需求保持、修订与执行 | 借鉴“状态识别”与“最终回答落实”分开检验的原则；其交互模拟不等同外部资料RAG，暂不新增模拟器服务 |
| [LongMemEval](https://github.com/xiaowu0162/LongMemEval) | 长期会话记忆、时间推理与知识更新 | 供扩展记忆任务参考；不替代当前外部证据多轮QA主评测 |

固定上游版本为`53fef6f5917c7e10c436f697e69a955dbc795d81`。MT-RAG的`RAG.jsonl`是110会话/842任务、每题五段的特定数据设置，不是系统的通用证据数上限。现有会话划分为22 dev/88 test，见`configs/mtrag_split_manifest.json`；已有使用记录保留，不把反复接触过的任务重新称为未见测试。

MTRAG-UN论文描述666个任务/六域，**当前公开reference文件实际为507个任务/四域**：ClapNQ142、Cloud131、FiQA77、Govt157。每个会话只发布一个选中任务，历史最多到第11轮；证据0–38段，其中130个任务没有给定证据。Banking/Telco尚未在该固定公开文件中发布。不裁成五段、不填充空材料，也不按任务答案选子集。该文件已完成507条读取、调度、完整导出和离线标签关联检查，尚未在当前版本生成507条答案。

## 公共组合与场景扩展

当前公共数据足以覆盖真实多轮检索、跨文档切换和若干长文本质量问题，先使用这些完整分区和统一协议，不为“有自己的benchmark”再造同类题目。MT-RAG仍承担主比较，MultiDoc2Dial扩展非技术资料和跨文档会话；Loong/ChatRAG按各自任务协议补充。数据集逐项报告，不把不同分数机械平均。

公共问答集通常没有到达时间、会话停顿、共享工作集和版本更新时间；这些是B/C系统评价需要补充的负载信息。可以直接在完整公共会话上声明到达过程、轮间停顿、并发和GPU/Host预算，复用现有runner，而不改问题或参考答案。已有保存结果先复用，只为尚未解决的容量/竞争问题运行必要负载。

若后续需要自建质量扩展，应作为一个有版本的场景集：以真实可溯源资料及明确版本关系为底稿，完整覆盖连续追问、纠正、条件切换、多资料比较、话题回访和部分可答；逐轮列明必要回答点、适用条件及支持来源，保留独立会话划分和标注复核。规模由覆盖缺口和结论所需置信度决定。先发布完整构造规则和开发/测试边界，再运行共同基线；不从系统已答好的片段拼出“优势测试”。这项扩展被允许，但本轮不在公共数据尚可复用时先生成新的合成题库。

## 协议与比较对象

| 协议 | 模型看到的历史 | 当前材料 | 回答的问题 |
|---|---|---|---|
| P1 | 数据集给定历史 | 官方给定来源，数量随任务 | 标准给定历史/材料下的质量；支持MTRAG-UN选中轮次 |
| P2 | 本方法此前实际生成并提交的QA | MT-RAG原始预检索来源 | 隔离上下文执行和缓存协同；不是完整在线检索 |
| P3 | 本方法此前实际生成并提交的QA | 本方法真实检索 | 完整A/B/C效果，计入解析、检索、选择、生成和提交 |

P2/P3沿用公开用户问题，后续问题并非交互用户模拟器。标准P1结果与采用自生成历史的P2/P3结果分别汇总。任务标签、参考答案和qrels仅离线评分使用。

矩阵的`comparison_scope: system`允许方法在`method.retriever_config`声明不同检索/意图机制，评价A/B/C整体。默认`execution`使用同一检索配方隔离B/C；若检索依赖各自实际历史，仍须核对保存的所选证据，不能仅凭配置相同就称材料相同。两类比较共用基座模型、资料范围、问题、采样、输出要求和资源口径。

预先固定、没有候选选择的配置可直接运行声明的test分区，不要求先消耗GPU做形式上的dev调参。真正调参或从开发结果选配置时，继续绑定相应冻结选择。开发流程不以所有评分工具、所有消融或所有指标完备为前置。

## 可复现入口

```bash
python scripts/fetch_mtrag.py
python scripts/fetch_mtrag.py --dataset mtrag-un
```

下载器校验一次固定文件摘要，再生成统计；取消对同一文件额外硬编码任务数/重叠数作为准入门槛。已有原始文件可加`--offline`。官方标注和所有原文保持不变。

`configs/benchmark_mtrag.yaml`是当前可执行的完整系统对照：Native B1使用已有last3混合检索，NativeWithA在原生执行上使用与ContextKV相同的conversational机制，ContextKV使用完整A/B/C。三者共享Cloud语料、生成模型及回答协议，固定配置，无参数搜索。Native与ContextKV比较整体质量/成本；NativeWithA与ContextKV帮助分析执行/缓存收益，仍需核对各自实际历史和证据。当前已安装P3索引只覆盖Cloud：对应205个官方任务，既有test分区实际164轮/方法。其他领域需准备对应索引后才能计入P3全域结果；P1/P2已经能够读取全部四域。

按[部署说明](deployment.md)准备固定引擎、索引、模型与32B解释服务后，先查看计划：

```bash
python -m bench.b6_joint_sweep --matrix configs/benchmark_mtrag.yaml \
  --stage test --job-timeout 3600 --output runs/mtrag-system-eval
```

确认本次研究问题需要生成对照后，在同一命令加`--execute`。不默认乘上并发、种子、重复或策略大矩阵；系统承载研究另按服务目标声明少量有意义负载点。

MTRAG-UN使用单个固定REBUILD方法作给定历史/来源的质量检查，复用相同执行器；不将它称为跨轮KV性能对照：

```bash
python -m bench.b6_joint_sweep --matrix configs/benchmark_mtrag_un.yaml \
  --stage test --job-timeout 3600 --output runs/mtrag-un-eval
```

真实Qwen3分词检查：507个任务均满足32768模型窗口，输入中位数1757、最大25507 tokens，29个达到4K、5个达到16K。五个任务的完整输入加输出预留超过原16K GPU池，因此该质量配置声明32K池和固定重建，不套用16K成本表、不裁题；仍需生成与评分后才能报告质量。此处只有tokenizer和候选构造，没有模型权重加载或推理。

所有给定历史和原文计入实际token预算，溢出显式记录，不改题或裁证据。官方竞赛format checker的十段上限与公开reference文件中部分任务不一致；提交校验和无损结果导出分开，不能为通过checker损坏测试数据。

## 质量、性能与资源指标

- **质量主指标**：复用官方参考答案、来源支持和可答性/歧义处理评价，按官方任务类别及领域报告。官方脚本提供`RL_F`、参考答案相关评分及IDK/underspecified调整项；名称和算法随固定脚本记录。必要时对关键任务作来源复核，不以引用格式、改写句式或模型输出长度替代回答有效性。
- **系统主指标**：完整响应均值/P95、会话累计等待；在预先声明服务期限后报告非截断达标吞吐。当前HTTP完整返回，内部引擎TTFT仅作诊断。
- **资源主指标**：相同资源下的服务能力，以及GPU/Host唯一KV槽位积分/完成轮次。解析/检索设备、模型驻留和实际调用成本计入系统；输入tokens、命中率和追加比例用于解释结果。
- **可靠性**：失败、截断、未完成轮次、提交/恢复一致性单列。CAS、版本身份与原文边界支撑正常运行，不将无关格式或缺少某个可选指标变成研发阻断条件。

官方离线关联入口会保留当前方法的真实输入和答案，再关联`targets`、`answerability`、问题类型与多轮标签。作者时间戳不进入模型输入，也不被误判为历史发生变化：

```bash
python -m bench.official prepare --input SAVED-PREDICTIONS.jsonl \
  --references data/mtrag-un/reference.jsonl --output runs/mtrag-un-labelled.jsonl
python -m bench.report SAVED-RUN.json --output runs/summary.json
```

后续官方评分复用`bench.official`和固定上游脚本。评分模型/版本与实际历史协议一起记录；同族模型评分可用于诊断，关键非劣/优胜结论再做相应复核与会话级统计。缺少评分保留为未评估，不触发无目的的补实验。

已有SGLang评分服务可使用统一HTTP入口，依赖在独立评价环境安装，评分不加载模型权重：

```bash
.venv-eval/bin/python -m bench.official generation-http \
  --checkout data/mtrag-official --input SAVED-LABELLED.jsonl --output runs/official-scores \
  --endpoint http://127.0.0.1:30002/v1 --model /media/ssd1/qwen3-32b \
  --judge-revision RECORDED-MODEL-REVISION --max-tokens 2048 --no-enable-thinking
```

该入口调用固定官方RB_llm、RAGAS RL_F、IDK和必要时的歧义评分；不另写评分公式。兼容旧式字符串调用，保持声明的greedy采样，使用LangChain SQLiteCache保存完整模型响应，各完成阶段原子落盘。相同输入和judge设置可续跑；不同答案/模型设置使用不同目录。评分代码改动不再强制重新生成主答案。本次隔离环境使用ragas 0.3.3、langchain 0.3.27、langchain-community 0.3.27和langchain-openai 0.3.29；完整依赖、原包装器与运行记录在`runs/public-main/`，未修改服务环境。

已完成的开发诊断集中保留结论，原始输入、答案和来源复核在对应`runs/`，不再将逐轮过程列成当前待办。

按21个会话整体重采样5000次，ContextKV−NativeWithA的请求均值差为+0.198秒，95%区间[+0.099,+0.309]秒；当前负载未显示净提速。ContextKV控制时间均值52.6ms，APPEND 29轮、REBUILD 135轮。原生＋A与ContextKV的当前资料ID集合仅84/164轮相同，实际历史仅25/164轮相同，故该差值是系统结果，不是相同输入的B/C因果效应。解析成本及更长输出参与总效果，不能把全部代价归到缓存控制。
